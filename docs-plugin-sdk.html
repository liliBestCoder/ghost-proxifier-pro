微内核与沙箱模型

一、 插件类型与运行体系深度解析

Ghost Proxifier 采用现代微内核与插件化架构。第三方代码永远不进入主进程内存空间，所有插件均以独立子进程受控运行。

1.1 插件的两大分类：内置插件 vs 外部插件

Ghost Proxifier 中的插件严格划分为两个信任层级（Two-Tier Trust Architecture）：

  • 内置插件 (Tier 1: Builtin / In-Tree)：
    随主安装包发行（位于 <InstallDir>\plugins\builtin\<id>\）。主程序在编译期固化二进制 SHA-256 白名单（trust_chain.h 中的 kBuiltinWhitelist）。拥有全局共享命名空间 (Global)，可直接调度管理系统内所有 Target 进程与出口节点。
  • 外部插件 (Tier 2: External / Standard / Out-of-Tree)：
    通过官方插件商店下载安装（registry）或开发者模式本地导入（local）。依赖 Ed25519 证书信任链签名验证。受属主单向隔离命名空间 (Owner-Only) 约束，只能读写自己名下创建的资源，严禁窥探或篡改其他插件或用户的全局配置。

1.2 进程拓扑：插件是谁拉起来的？

很多开发者会好奇：插件是一个 DLL 注入到主进程，还是一个独立进程？答案是：绝对的独立子进程！

  • 启动调用链路：ghost_proxifier.exe (主进程) ➔ supervisor.cpp (监督器) ➔ 启动 ghost_plugin_host.exe (插件宿主进程) ➔ 拉起具体插件子进程。
  • Job Object 物理绑定：ghost_plugin_host.exe 在启动插件时，使用 CREATE_SUSPENDED 挂起进程，将其加入 Windows Job Object（设置了 JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE），然后再 ResumeThread。这保证了一旦宿主退出或发生崩溃，所有插件子进程会被 Windows 内核强制一次性物理回收，绝不会在后台残留僵尸进程。
  • Low-IL 与特权剥离沙箱：外部插件默认在受限令牌（Restricted Token）与低完整性级别（Low-IL S-1-16-4096）下运行，受 Windows 内核的 No-Write-Up 策略保护。插件无法写入当前用户的中高完整性文件目录，彻底隔绝恶意代码修改宿主配置。

1.3 Token 体系与注入机制（为什么不用命令行或环境变量？）

Ghost Proxifier 系统中存在三种 Token，各司其职：

  1. X-Ghost-Token：主界面（UI WebView）专用的全权会话 Token，外部插件绝对无法获取。
  2. X-Ghost-Host-Token：宿主管理进程特权 Token，仅用于握手与宿主健康同步。
  3. X-Ghost-Plugin-Token：宿主为每个插件独立签发的 128 位随机 GUID 临时凭据。
🛡️ Token 是如何安全下发到插件里的？

答案是：严格通过进程的标准输入流（stdin）第一行 JSON 握手数据下发！

数据只在主宿主与插件两个进程的内核缓冲区中瞬时流转，不落盘、不广播，由插件在内存中解析持有，重启即换。

管道握手链路 宿主 (ghost_plugin_host) ──[ stdin 第一行 JSON 数据流 ]──▶ 插件子进程
JSON 
{
  "v": 1,
  "pluginId": "io.github.yourname.my-plugin",
  "token": "4a7f9b8c-1234-5678-abcd-ef0123456789",   <--- 插件内存临时凭据
  "apiBase": "http://127.0.0.1:23551",
  "dataDir": "C:\\Users\\...\\AppData\\Local\\GhostProxifier\\data\\...",
  "stopEvent": "GhostPluginStop_..."
}
⚠️ 为什么绝不通过命令行或环境变量传 Token？
  • 命令行传参极度危险：Windows 下同一登录会话中的任何普通程序，都可通过 WMI 查询、Process Explorer 或读取目标进程 PEB 查看到完整的启动命令行。如果把 Token 写在命令行参数里，等同于向本机所有运行中的程序明文广播凭据！
  • 环境变量存在继承泄漏：环境变量极其容易在调用系统 API、启动子进程时被隐式继承或扩散，同样可通过 PEB 轻松跨进程读取。

1.5 为什么做这种分级别与多权限隔离？（架构初衷）

产品定位：浏览器的软硬件指纹伪装通常交由专业的指纹浏览器处理，而 Ghost Proxifier 专注于系统底层的 Winsock 接管与进程级网络流量治理。分级信任源于以下四个核心考量：

🌐
1. IP 层级的纯净与精准隔离
用户往往为不同进程绑定了不同的出口 IP（包括昂贵原生住宅 IP）。分级隔离确保外部插件绝无法越权篡改其他进程路由，更不能串用他人独立 IP，从底层杜绝 IP 交叉污染。
🛡️
2. 企业安全审计与凭据保护
外部沙箱插件受“凭据只写不读”约束，读取节点时密码恒被强行掩码为 ******，彻底封死脚本窃取企业代理账密的可能；拉进程、建隧道等动作均有审计日志与原生人工审批。
⚡
3. 开发者日常 Vibe 编程与工具扩展
插件作为独立进程运行在 Job Object 与 Low-IL 内，崩溃由内核即时回收，不会拖垮 Ghost 宿主或影响其他插件；开发者可放胆快速原型迭代，无惧代码写崩破坏系统环境。
🔀
4. 多个 VPN / 代理客户端混用共存
Ghost 采用细粒度的进程级精准接管，不篡改系统全局网络栈。通过限制外部插件随意操作出网（ghost.egress.v1 闸门），避免私自劫持全局流量造成网络环路。

01

端口动态分配 (Port 0)

插件内置的本地 Web 服务必须绑定到回环地址 127.0.0.1 且端口指定为 0（由 Windows 内核随机分配空闲端口）。
严禁硬编码固定端口，严禁使用 80 端口与 Ghost 宿主的 23551 端口（宿主安全策略会直接拒绝加载）。

02

握手回执携带 uiUrl

插件在从 stdin 读取完握手帧后，向 stdout 输出的第一行 JSON 回执必须携带 uiUrl 属性：
{"v": 1, "ok": true, "uiUrl": "http://127.0.0.1:53211/"}
若未提供或 URL 不合法，宿主将丢弃该属性并按无界面插件处理。

03

严格跨源隔绝准则

前端页面绝对不能直接获取或持有 Ghost 的主凭据或插件 Token！ 前端如需与 Ghost 数据联动，必须请求插件自己的本地 HTTP 服务接口，由插件后端完成鉴权与校验后代调 Ghost Control API 并过滤结果返回。

04

CSP 与 DNS Rebinding 防护

插件本地 HTTP 服务的静态资源应配置 Content-Security-Policy，设置 frame-ancestors http://127.0.0.1:23551（取自握手中的 apiBase），防止未授权网页嵌入面板；同时严格校验请求的 Host 头是否等于 127.0.0.1:<port>。

⚠️ 高危动作运行时二次审批 (Runtime Approval) 核心机制
  1. 受控命令范围：针对 plugin.target.launch（启动目标）、plugin.upstream.create（新建节点）、plugin.tunnel.connect（发起代理隧道）等高敏感动作，即使清单已声明权限，首次触发时仍会触发系统原生确认弹窗让用户核对执行快照。
  2. 30 秒等待超时：系统等待用户人工决策的超时时间上限为 30 秒 (kApprovalTimeoutSec = 30)。若点击“拒绝”，API 立即返回 approval_denied；超时未操作，自动撤销并返回 approval_timeout。
  3. 并发限制：每个插件同一时刻仅允许存在 1 个在途审批请求 (kMaxPluginApprovals = 1)。并发发起高危操作将直接返回 busy 或 rate_limited。
  4. 客户端超时配置黄金法则：插件在调用上述三类高敏接口时，HTTP 客户端请求超时（Timeout）必须设置为 35~40 秒以上！ 若误用常规的 5 秒超时，将导致在用户还未来得及点击确认时，客户端就因套接字超时而提前断开并抛出异常。

安全开发规范

七、 总结与最佳实践准则

在开发与向官方提交插件前，请务必核对以下 5 条核心准则：

准则 01

Token 永不落盘

切忌将 token 输出至普通日志、写到本地临时文件或放入命令行参数。Token 只应存在于插件进程的受保护内存中，进程退出即销毁。

准则 02

UI 严格跨源隔绝

UI 网页如需访问 Ghost 数据，必须请求插件自己的 HTTP 服务由插件代调，严禁将 Token 传入 iframe。内置 Web 服务必须配置 frame-ancestors 与 Host 头校验。

准则 03

Fail-Closed 永不回落直连

网络代理隧道建立失败时，直接切断连接，绝对不可擅自回退为本地直连，以免造成真实环境下的真实真实 IP 泄露与网络污染安全事故。

准则 04

版本号规范与 minAppVersion

提交官方审核前，务必在 manifest.json 中严格遵循语义化版本号，并确保 minAppVersion >= 1.2.2，确保运行在版本化权限组之上。

准则 05

官方审核渠道：统一前往官方开发者 QQ 群

官方插件审核不设立任何第三方代理渠道，请统一前往 Ghost Proxifier 官方开发者 QQ 群（群号：945138408） 提交工单和 .gpkg 审核材料。官方技术团队将在群内协助进行沙箱运行测试与证书代签。
